Slice: {slice}

Your one job: walk this unit until you could type the patch, put that closed set in the context index of session-plan.md (below `<!-- gathered -->`), write the Approach, then report. The main session reads the task file and one full packet, then edits. Do not leave a lookup it still has to do.

1. Read session-plan.md{task_step}{request_step}. State the outcome in one line: what will be observably different.
2. Walk the edit. Read the function you would change. In the same turn, batch-read every call and field the patch must get right. Stop when you could type the patch, not when you have a menu of files. Use `wdb__lookup` when it is connected, otherwise `{py} tools/find.py`. If `wdb__lookup` is still connecting, wait and use it; do not probe with `{py} -c`, `--help`, or a shell chain. Once it has answered, do not switch to `find.py`. For a platform-specific problem (mobile, web, touch, keyboard, export), also search `project.godot` and `export_presets.cfg`. A pattern that contains `|` is alternation only with `regex: true`. Prefer one simple pattern per entry in the same `reads` list, with `all=true` when you need the whole result.
3. Core is that closed set, scoped to funcs. `--why` is `edit` or a one-line contract (what the patch must keep true). Remove every seed item this unit will not read. Do not leave a whole `.gd` in core when the edit is a few functions. A candidate is only a branch you could not close from the request. A candidate that means "maybe the handler" is a failed walk: read it and put the real func in core, or drop it. Do not leave the card's "use find.py" line as the plan.
4. Scope a long file to the funcs the patch touches. A script is `add-func PATH NAME` (a line range on a `.gd` is stored as the funcs that cover it, because line numbers slide). A doc is `add-doc PATH#Heading`, or `add-doc PATH --lines A-B` / `add-file PATH --lines A-B` for a range that is not a script (one file may hold several ranges; `rem` the whole-file item first). `wdb__lookup action=doc path=DOC` with no heading lists headings and line numbers; `action=names path=FILE` lists funcs; `action=xref pattern=TEXT path=FILE` finds lines in data files such as `scripts/data/locale/en.po`.
5. Change the index only with `{py} tools/slice.py adjust`. One batch for the index: `{py} tools/slice.py adjust batch --op "rem K4" --op "add-func PATH NAME --why edit" --op "set-condition K5 --when 'read if ...'"`. Then, in its own call, `{py} tools/slice.py adjust approach --text "..."`. The Approach is the edit in the order you would type it, under 4000 characters and with no heading lines: edit order, the prose patch, invariants, the prove command, and deliberate omissions as one-line contracts. `--reason` is optional. `adjust --help` lists every op; `--dry-run` first prints every error.
6. Run `{py} tools/slice.py expand --check`. Fix every item it names until it passes.
7. Finish with `{py} tools/slice.py adjust report --text "<2-6 lines: does the door or job fit, where the cause of each problem is, what the main session should know first>"`. Add `--halt "<reason>"` only when the slice should not start as opened (wrong door or job, the task is contradictory, or a needed file is missing). The User then decides.

Batch your reads. A turn is one model round: every tool call you make in parallel in that round counts once. Put independent reads in one call, not one round each. Do not list trees or run `--help`. When `wdb__lookup` is not connected, make the same reads as parallel `{py} tools/find.py` and `{py} tools/docs.py` commands (no `;` and no unquoted `|`). A doc read without a heading is its outline with line spans; then read the heading or the line range.

There is no turn budget. The run stops if the context is compacted before you report. That stop writes the reason and does not start the main session. Finish the index, the Approach and the report before the context fills.
